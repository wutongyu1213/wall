# 寻物启事：怎么开通、怎么用、坏在哪

## 一句话

新页面 `lost-found.html`：丢了东西、捡到东西都贴这里。**发帖、列表、筛选、标已找到、申请删除都做好了，但必须先在数据库执行一段脚本，否则只能看不能发。**

---

## 为什么不能像表白墙那样直接发

这不是偷懒，是实测出来的硬限制（2026-11-15）：

| 尝试的通道 | 结果 |
|---|---|
| `wall` 表匿名 INSERT | 401 `permission denied for table wall` |
| `wall_candidates` 匿名写 | 401 `permission denied` |
| Storage 桶匿名上传 | 400 `new row violates row-level security policy` |
| `fn_wall_post` 传新 tag | 400 `tag_invalid：标签需为喜欢/告白/感谢/祝福/思念` |

表白墙能发帖，是因为它有一个专用的数据库函数；那个函数把标签写死成 5 个值。
**所以「寻物启事」必须自己有一个写入函数，没有第二条路。**

---

## 开通：三步，约 3 分钟

1. 打开 `https://supabase.com/dashboard/project/dpceuvqtwvhoipxhozxz/sql/new`
   （没有权限就找项目创建者要）
2. 把仓库里 [`sql/05-寻物启事.sql`](../sql/05-寻物启事.sql) **全文**粘贴进去
3. 点 **Run**

然后刷新 `https://wutongyu1213.github.io/wall/lost-found.html`：
页面顶部那条黄色「这个功能还没开通」会消失，发布按钮变亮。

> 页面会自己探测（调 `fn_lost_ready`）。**不需要重新部署前端**——SQL 一执行，页面立刻可用。

---

## 数据放在哪

不新建表，直接复用 `wall`（这样后台的隐藏/删除、前台读取通道全都不用改）：

```
love_tag      = '寻物' | '招领'      ← 类型
target_name   = 物品名称
love_msg      = 一句话摘要（后台列表和邮件读这列）
lost_status   = 'open' | 'found'     ← 新增列
lost_meta     = {kind,item,place,desc,contact}  ← 新增列
user_key      = 设备身份（用于「我的投稿」和限流）
```

> `fn_lost_list` 用 `security definer`：将来执行 `02-收回表读权限.sql` 后 anon 会失去 `wall` 的 SELECT，
> 若用调用者身份运行会立刻失效。函数内部已用 where 限死只返回寻物/招领，不构成越权读取。

**代价**：寻物帖会出现在 `wall` 表里，所以表白墙做了 4 处过滤
（Edge 通道 / 表直读 / 本地快速缓存 / 我的投稿），否则寻物帖会混进表白流，还会被按性别分到蓝粉两区。

---

## 审核怎么办

- **人工**：后台「🗣️ 内容」页照旧能看到、隐藏、删除——因为它们就在 `wall` 表里。
  列表里会显示 `🔍 寻物启事` 标签，不会和表白混在一起。
- **AI**：巡检脚本已适配。寻物启事天然需要「联系方式 / 到哪认领」，
  所以对这两类**只豁免 pii 和 contact**，辱骂、性暗示、自伤、诈骗仍照常标记。
  不这样改的话，每条寻物启事都会堆进「风险待确认」，红点会变成噪音。

---

## 作者能做什么

- 只能标记**自己发的**（服务端比对 `user_key`，不是前端判断）
- 「申请删除」走现有的 `fn_wall_appeal`，进后台申诉队列，管理员确认后才删
- 满 30 天自动不出现在列表（前端按 `created_ts` 过滤，不删数据）

## 已知限制（别踩）

| 限制 | 说明 |
|---|---|
| 没有图片 | 要传物品照片得再改一次存储桶策略，这次没做 |
| 没有「已找到」自动过期 | 标了 `found` 会一直显示「已找到」，需要作者或管理员处理 |
| 联系方式全公开 | 手机号会直接显示。页面已提示「建议写班级或交到某处」，但拦不住 |
| 不能改已发布内容 | 没有编辑功能，发错只能删了重发 |
| 「谁发的」靠 user_key，可被伪造 | user_key 对匿名可读（历史遗留）。所以「标记已找到」只能防误操作，防不了恶意 |
| **数据库层自动审核** | wall 表有 BEFORE INSERT 触发器（`check_content`/`wall_ins_guard`）：电话/网址/`宿舍`/`地址`/`微信号` 等词、`target_name`>4字、正文>200字 → 行被置 hidden。所以物品名不进 `target_name`（只进 lost_meta），发布函数会检测并如实返回 `auto_hidden`，页面提示「换个说法」——不会静默消失 |
| anon 看不到被拦的行 | wall 有 RLS：匿名 REST 只能看到 `status='ok'` 的行。hidden/flagged 行只有后台和 SQL 可见（这就是为什么「发布失败」的帖子在你手机上查不到，但老师后台能看到） |
| 与表白共用统计 | 后台「可见表白」数会把寻物帖算进去 |

## 回滚

```sql
drop function if exists public.fn_lost_post(text, text, text, text, text, text, text, text);
drop function if exists public.fn_lost_resolve(bigint, text);
drop function if exists public.fn_lost_ready();
drop function if exists public.fn_lost_list(int, text);
drop index if exists public.wall_love_tag_ts_idx;
```

函数删掉后，页面会自动回到「未开通」状态（不是白屏）。
已发布的寻物帖仍在 `wall` 表里，需要单独删除。
